# Development oversight milestone

PAGENTWORKFLOW's purpose is persistent development oversight alongside Codex.
Codex implements changes. PAGENTWORKFLOW retains reviewed project context and
returns evidence-based assessments for humans to consider. It cannot approve,
merge, deploy, write code, update knowledge, or execute a suggested command.

## Workflow and report contract

```text
tracked fictional knowledge + supplied fictional diff text
                        |
              validate and hash evidence
                        |
                    Lead Agent
                        | review_ui (same complete evidence bundle)
                     UI Agent (no tools)
                        |
                 Lead structured analysis
                        |
           validate citations and goal authority
                        |
             JSON report for human review
```

`oversight/evidence.py` loads one fixed, trusted, version-controlled knowledge
fixture and parses bounded diff text. It does not fetch source documents, open
diff paths, apply patches, or inspect the checkout represented by the diff.
`oversight/review.py` assembles context, runs the agents, validates the model's
structured `Analysis`, and assembles the report independently of transport.
`oversight/demo.py` is the explicitly synthetic model substitute for no-network
demonstrations. `oversight/__main__.py` is the small CLI and optional live adapter.

Reports carry the knowledge snapshot and hash, diff hash and numbered hunk
evidence, completed UI review, and these distinct categories:

| Report field | Interpretation |
| --- | --- |
| `verified_changes` | Deterministic file operations and line counts from the supplied diff only |
| `documented_module_matches` | Approved exact-path associations and documented dependencies, not a traced dependency graph |
| `unmapped_paths` | Paths without an approved module-objective mapping; missing knowledge stays explicit |
| `analysis.apparent_intent_unverified` | Inferred reason for the change; author intent is not established |
| `analysis.goal_alignment_assessments` | Judgment of support, potential conflict, or uncertainty against approved goals |
| `analysis.potential_risks` | Possible functionality/UI regressions with priority and a verification step |
| `analysis.speculative_recommendations` | Opportunities for improvement, not approved new requirements |
| `analysis.recommended_next_steps` | Proposed development work and acceptance checks for human consideration |

Every analysis item requires citations. Alignments require both the exact
approved goal revision and diff hunk evidence. Unknown/stale knowledge references,
non-approved goals, missing citations, nonexistent patch lines, header references,
and ranges crossing non-hunk lines fail the review. Model output cannot add
fields such as `verified_findings`; verified observations are generated by code.
These checks establish provenance, **not semantic correctness or completeness**.
Prose may still be wrong or overlook an issue; human review remains necessary.

`diff.patch:17` means line 17 of the **supplied patch**, not line 17 of `app.js`.
The `supplied_diff.lines` catalog maps it to file, change kind, old/new source
line, and exact text. `knowledge:booking@1` identifies an entry and revision in
the embedded knowledge snapshot. Paths, source metadata, and comments are data,
never authorization or instructions. The UI always receives the same complete
bundle even if the Lead's tool arguments omit or distort it.

## Run the demonstration

From a Python 3.10+ virtual environment with `requirements.txt` installed:

```bash
python -m oversight --demo
python -m oversight --diff-stdin < examples/oversight_change.diff
# Optional: save the report under the already-ignored artifacts directory.
mkdir -p artifacts
python -m oversight --demo > artifacts/oversight-demo.json
```

The first two commands produce the same report in `offline_demo` mode. They run
the real SDK tool/delegation/output-parsing path with deterministic synthetic
responses built from the supplied evidence. They do not load `.env`, inspect an
API key, contact any service, or incur API/hosting costs. This demonstration
checks plumbing, citations, and report structure; its deliberately generic
analysis is **not a live AI assessment**. A different fictional diff may be
supplied over stdin; no arbitrary knowledge root or file-path option exists.

The bundled patch proposes an accessible menu name (`diff.patch:8`) and removes
`event.preventDefault()` from form submission (`diff.patch:17`). A human reviewing
it should investigate whether native form navigation conflicts with the approved
local booking objective (`knowledge:booking@1`). That is a potential regression,
not a browser-tested fact. The patch is never applied to `sample_frontend`.
The scripted SDK test supplies this specific analysis; the offline CLI keeps
its assessment generic instead of pretending to discover it with a live model.

Inspect `mode`, `completed_ui_reviews` (must be 1), evidence hashes,
`verified_changes`, the UI review, alignment citations, and proposed checks in
the saved report. Keep the report's evidence snapshot with it. No persistent
conversation, automatic learning, or background process exists.

## Optional live oversight review

This milestone was implemented and tested offline. Its live model quality and
real API authentication have **not** been validated. If separately authorized,
configure an OpenAI API key in your process environment using your local secret
handling method, then explicitly opt in:

```bash
python -m oversight --demo --run-live --model gpt-4.1-mini
# Or use only fictional input supplied over stdin:
python -m oversight --diff-stdin --run-live < examples/oversight_change.diff
```

The oversight CLI deliberately does not load `.env` or accept a key as an
argument. Never paste a key into a diff, knowledge file, chat, or committed file.
The existing `h2o.py` and `live_test.py` retain their documented `.env` behavior.
`mode: model` means model-backed execution, not verified recommendation quality.

A normal successful live run has **three model requests**: Lead delegation, UI
review, Lead synthesis. Only one UI attempt and two Lead turns are permitted;
additional delegation is denied before another UI model request. Each request
is limited to 2,400 output tokens and a 45-second timeout; the workflow timeout
is 180 seconds. Automatic SDK/client retries, tracing, and Responses storage
are disabled. The endpoint is fixed to the official OpenAI API; normal machine
HTTPS proxy/CA settings still apply.

OpenAI API usage is billed separately from a ChatGPT subscription, for each
request's input/output at the selected model's current rates. Repeated context
and specialist output contribute to input tokens; a failed run can still cost
money. These bounds are not a dollar cap, persistent rate limiter, or billing
authorization. Review API usage/billing and project limits before rerunning.
No live calls, new infrastructure, provider accounts, or deployment were needed
to implement this milestone.

## Limits and errors

Inputs are limited to 32 KiB, 800 patch lines, and eight unique files; knowledge
is limited to 24 KiB and 40 entries. The diff parser accepts LF UTF-8 Git unified
text diffs with matching hunk counts, ordinary `100644` files, additions/deletions,
and no-final-newline markers. It rejects traversal/absolute/hidden paths, renames,
binary/combined diffs, mode changes, symlink modes, duplicate files, overlapping
hunks, extra trailers, malformed counts, controls, and oversized input. It does
not prove that a diff applies to any real base commit. This restricted subset is
intentional; unsupported input fails rather than being silently truncated.

Success is JSON on stdout with `ok: true`; failures emit only a safe JSON error
on stderr and exit 1, without a success report. Argument errors exit 2.
Codes include `knowledge`, `diff_input`, `citation`, `authority`, `delegation`,
`response`, `authentication`, `configuration`, `api_limit`, `unavailable`, and
`review_failed`. Wrapped specialist errors preserve their classification without
printing raw provider bodies, input text, paths, or keys. Provider diagnostics
are suppressed by the CLI. Check the code, correct the input/configuration, and
retry manually. Reports intentionally contain supplied fictional evidence, so
do not submit sensitive material; this is not a data-loss-prevention filter.

## Validation and next milestones

```bash
python -m unittest discover -s tests -v
python live_test.py  # default skip; no model calls
```

Offline tests cover authority/source metadata, evidence hashes and bounds, diff
provenance, rejected formats, stale/invalid citations, non-approved goal rejection,
real SDK delegation and structured synthesis, pinned specialist input, repeated
tool-call denial, errors, CLI opt-in, and unchanged source/MCP behavior. They
substitute model responses and local API boundaries; they do not test live model
quality, browser behavior, external OAuth, or Python 3.10 runtime behavior.

Recorded validation (November 16, 2026, Linux/Python 3.12.14,
`openai-agents` 0.24.0): **83 offline tests passed** (59 preserved plus 24 new).
Both demonstration entry paths returned identical valid JSON; the supplied
patch passed `git apply --check` against the bundled sample without applying it.
Dependency consistency, Python 3.10 syntax, and whitespace checks passed. The
existing live harness returned its default no-call skip. No live oversight test,
credential access, merge, deployment, or paid API call was performed.

Before reviewing real Codex PRs, separately scope and approve:

1. An allowlisted read-only GitHub adapter with minimal credentials, immutable
   base/head SHAs, complete diff retrieval, truncation detection, and the same
   fail-closed format/size limits. No such access is added here.
2. Human-approved real project knowledge, conflict/freshness handling, and an
   audit record linking every review to knowledge revision and exact PR/commit.
3. Safe bounded source context using the existing reader's security design,
   explicit module mappings, and better dependency evidence; no unrestricted root.
4. One explicitly authorized fictional live oversight validation and a human
   quality review, then regression cases for real review failure modes and costs.
5. If desired, an MCP adapter returning `OversightReport` through the existing
   scoped authorization/service boundaries. Hosting and ChatGPT OAuth remain
   separate approvals; do not deploy the preserved integration automatically.

Further specialists can reuse the existing registry and manager-tool pattern
after their review-only roles are designed and tested. No Architecture,
Developer, or QA agent is introduced here. Any future code-changing operation
needs a separate trusted human-approval design, not a model-supplied flag.
